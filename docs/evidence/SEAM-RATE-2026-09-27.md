# The seam rate of an engine with its own host — 2026-09-27

Type: EVIDENCE RECORD
Build: `4602d7b` (`feature/ph-40-the-engine-a-broker-settles-against`), production composition, 30 markets
Host: the development machine (16 cores, WSL2), with nothing else started for the run; the Orbit broker stack's own services were running as always
Raw samples: below, one per minute from `/metrics`

---

## 1. Why this was measured

The Human Owner saw 1,762 recorded seams in one day on PH-39's venue and asked
whether that is how OTC engines are. It was measured on a machine running
builds, test suites and a fleet of agents beside the engine. This asks the
question with the engine alone, and then with the CPU taken from it on purpose.

## 2. Result

| condition                                           | new automatic reopenings           | worst gap between passes |
| --------------------------------------------------- | ---------------------------------- | ------------------------ |
| the engine alone, 30 min                            | **0**                              | 0.17 s                   |
| 16 busy processes on 16 cores, 5 min                | **0**                              | 1.57 s                   |
| 32 busy processes on 16 cores, 5 min                | **0**                              | 0.02 s                   |
| recovery, 5 min                                     | **0**                              | 0.01 s                   |
| the host **slept**, twice (≈3 h and ≈80 min behind) | **30 per outage** — one per market | —                        |

Recorded seams across the catalogue at the end: **60** — the two sleeps, one
seam per market each, and nothing else. After each sleep the venue reopened
itself and published on; no operator touched it (ADR-0020, PH-39).

**What this says.** Contention does not seam this engine: at twice as many busy
processes as cores its passes still ran within 1.6 s of each other against a
15 s bound. A seam needs the process stopped outright — a host that sleeps, a
VM that is paused, a clock that jumps — and a server that does not sleep does
not produce them. The 1,762 of PH-39's day were that machine, not the engine.

**What it does not say.** Thirty minutes alone is not a month in production, and
a host with less headroom than sixteen cores for thirty markets was not
measured. The metric that would show either is `otc_market_reopenings_total`,
and an operator should alert on it moving.

## 3. How it ran, including what went wrong

`seamRate.sh` started the venue on its own state directory
(`~/.otc-local/measure-ph40`, never the live venue's), sampled `/metrics` each
minute for 30 minutes alone, and was then meant to run the load phases. It hung
instead: with no load processes, `wait` on an empty list waits for every child,
the venue included. While it hung the host slept twice — which is the fourth row
above, measured by accident. The load phases were then run against the same
venue with the `wait` fixed (`loadPhase.sh`), from 17:59 to 18:15 UTC.
