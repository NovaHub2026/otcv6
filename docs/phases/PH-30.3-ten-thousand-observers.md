# PH-30.3 — Ten Thousand Observers Held, From Several Processes, Memory Measured At The Target

Type: SUBPHASE TECHNICAL DOCUMENT
Identifier: PH-30.3
Parent: [PH-30](PH-30-release.md)
Status: ACTIVE
Created: 2026-09-06

---

## 1. Objective

Measure what `CYCLE-8-OBSERVER-LOAD.md` said was the next honest step and not
an extrapolation: ten thousand observers on one venue, driven from several
harness processes so the instrument is not what is measured, with the venue's
resident memory and delivery latency recorded at the target — and the ceiling
written down as a number a broker can plan against.

## 2. What is run

`tools/sim/src/observerLoad.ts` already opens N streams from one process and
measures delivery; PH-30.3 adds `observerFleet.ts`: a driver that spawns K
worker processes, each holding N/K observers over the multiplexed stream
(eight assets per connection, the shape a page has), holds them for a window,
and reports per worker gaps, duplicates, p50/p99 delivery latency; the venue's
`/metrics` is sampled before, during and after for `otc_stream_connections`,
`otc_stream_subscribers` and `otc_process_resident_bytes`. The evidence is
recorded in `docs/evidence/PH-30-TEN-THOUSAND-OBSERVERS.md` with the machine,
the commit and the numbers, at 1 000, 2 500, 5 000 and 10 000 observers.

## 3. Acceptance criteria

1. At the largest size the machine holds, every observer sees contiguous
   ticks with no gap and no duplicate; the size reached is the record's
   headline, whether or not it is ten thousand, and the reason it stopped is
   named.
2. Resident memory per connection and delivery p99 are recorded at every
   size; the marginal cost per observer is derived.
3. The record names the ceiling for a broker: the observers one venue on this
   class of machine holds, and what stops it (file descriptors, CPU, memory).
