## 1. Objective

A `CoordinatedStore` that two processes can share, passing PH-14's conformance
battery **unchanged**.

## 2. The battery is the specification, and it does not move

PH-14.1 §5 made the contract executable precisely so this substitution would be
checked against properties rather than prose. The failure mode it was built
against is the one available here: meeting the backend halfway. Relaxing a
property to fit an implementation converts the battery from a specification into
a description, and a description of a broken store still passes.

So `describeCoordinatedStore` is invoked against the new store with no
modification. If a property cannot be met, the backend is wrong.

One thing the battery needs and cannot assume: a controllable clock. Expiry is
judged by the store, and a battery that could only test it by sleeping would be
slow and timing-dependent. The SQLite store takes an injected `Clock` like the
in-memory one — the persistence is in the storage, not in where the time comes
from.

## 3. Why `node:sqlite`

Zero dependencies. Node 24 ships it, the repository already pins Node 24 in
`.nvmrc`, and the dependency guardrail exists because a package acquiring a
dependency it should not have is a failure mode this project has already
measured.

More importantly it is **transactional**. PH-14.1 argued that a fence check and
a write must not interleave, and satisfied it in memory by keeping the critical
section free of `await`. That argument does not survive two processes. A
transaction is the real form of it: `BEGIN IMMEDIATE`, read the grant, compare,
write, `COMMIT` — and SQLite's write lock makes the section atomic across
processes rather than merely uninterrupted within one.

The cost is stated plainly: this is correct for multiple processes on **one
machine**, on a local filesystem. It is not a distributed store, and SQLite over
a network filesystem is a documented way to corrupt a database. Multi-machine
deployment needs a networked backend, and PH-15's exclusions say why that is not
built here.

`engines` moves to `>=24.0.0`. It has been the developed-on version throughout
and is what CI runs; on 22.5 to 23 `node:sqlite` needs an experimental flag, and
a store whose correctness depends on a flag being passed is not one.

## 4. The schema is the contract, restated

Three tables, and the shape of each follows from a property the battery asserts:

**`lease`** — one row per asset: holder, token, granted_at, expires_at. Plus
`high_water`, retained when a grant is deleted, because expiry must never
recycle a token. That column exists because of one battery property, and a schema
that merged it into `token` would pass every test except that one.

**`record`** — the published entries, keyed by `(asset_id, position)` with
position an insertion ordinal rather than a sequence. Sequences are sparse after
a seam, so they cannot index the table; the ordinal preserves order and a
separate index on `(asset_id, sequence)` serves lookup for the ticks that have
one.

**`state`** — the market checkpoint, one row per asset, written under the fence.

## 5. What has to be gotten right, and is easy to get wrong

**A rejected write must leave the database untouched.** The in-memory store
validates a whole batch before mutating anything; in SQLite that is a
transaction rolled back. The battery asserts it — "applies nothing at all when
part of a batch is bad" — and a store that wrote the good prefix before hitting
the bad tick would leave a record no single writer could have produced.

**The fence check belongs inside the transaction.** Reading the grant, returning
to JavaScript, and then writing is the race the whole design exists to prevent,
reintroduced one layer down.

**Reads must not be able to see a partial write.** `journal_mode = WAL` with the
default isolation gives that; it is set explicitly rather than relied upon.

## 6. What is built

`packages/runtime/src/sqliteStore.ts`

- `SqliteCoordinatedStore` — `LeaseStore`, `StateStore` and `ReplicationLog`.
- `open`/`close`, and a schema created on first open.

`packages/runtime/src/sqliteStore.test.ts`

- `describeCoordinatedStore('SqliteCoordinatedStore', …)`, unmodified.
- Durability and cross-connection tests the in-memory store cannot have.

A networked store, connection pooling, migrations. The schema is created once and
`STATE_RECORD_VERSION` already governs the payload it carries.

### The test that had to exist

Nothing in a single-process suite can test "several processes, one leader". The
in-memory store's atomicity argument was "the critical section contains no
`await`", which is true and says nothing about a second process.

Measured: swapping `BEGIN IMMEDIATE` for a deferred `BEGIN` left **every other
test in the package green**, including a first draft of the race itself — one
round, eight processes, and the winner committed before the losers opened their
transactions, so nothing contended. The test now runs 150 contended rounds
across 6 processes; the same plant fails it.

### Each guard watched failing

Thirteen defects planted in turn.

| Planted defect                                            | Tests that failed |
| --------------------------------------------------------- | ----------------- |
| The high-water mark is dropped when a grant expires       | 8                 |
| `clearLease` wipes the high-water mark too                | 8                 |
| Renewal bumps the token                                   | 2                 |
| A refused write is committed rather than rolled back      | 1                 |
| `expectNext` is rebuilt as `head + 1`, closing a seam gap | 1                 |
| The fence check is skipped on append                      | 1                 |
| The fork comparison is dropped                            | 1                 |
| The lease is not persisted, only the record is            | 31                |
| `BEGIN` instead of `BEGIN IMMEDIATE`                      | 2 (the race)      |
| No `busy_timeout`, so contention reads as failure         | 2 (the race)      |
| The WAL retry gives up after one attempt                  | 1 (the race)      |
| WAL is skipped for file-backed databases too              | 1                 |
| Reads order by sequence rather than insertion position    | **0 — see below** |

### One plant that no test catches, recorded rather than claimed

`ORDER BY position` and `ORDER BY sequence` return the same rows in the same
order for every record this system can produce. They differ only on a tie — a
seam whose resume sequence is `lastSequence + 1` — and SQLite breaks that tie in
rowid order, which _is_ insertion order.

So the column is chosen because it does not depend on an undocumented
tie-break, not because a test distinguishes it. Claiming coverage here would be
the thing this project keeps finding in its own guards.

### Found while building it

**The store was concurrency-safe in every method and not in its constructor.**
Eight processes opening the same new database at once had seven die with
"database is locked" — `PRAGMA journal_mode = WAL` needs an exclusive lock and
SQLite refuses immediately rather than invoking the busy handler, which
`busy_timeout` does not change. The open path now reads the mode first, and on a
refusal waits on an empty immediate transaction rather than spinning.

**Requiring WAL unconditionally broke the entire conformance battery**, which
runs in memory: SQLite keeps `:memory:` in `memory` mode however often it is
asked. It ran green for as long as nothing re-ran the battery after the WAL
change, and the tie-ordering test written minutes later surfaced it.

### Fixed in scope, in another package

Adding a test that spawns processes made the unit suite busier, and
`packages/lab/src/ruin.test.ts` — a PH-13 Monte Carlo bound check, 2,000 paths
of up to 20,000 events (the two numbers were transposed here until 2026-09-02) — went from 2.5 seconds to 6.5 and failed the 5-second
timeout.

This is verbatim the failure `testCost.test.ts` was written to prevent: "it
appears when the suite gets busier, and it looks like the new work broke
something". The new work did not break it. It revealed that it had never had
headroom, in the fast project, for a simulation that is statistical by every
definition this project uses. Moved to `ruinSimulation.stat.test.ts`.

The barrier in the race test was also cut from 400ms of six-way spinning to
3ms, because cost there is not free to anyone else.
