# PH-22.1 — An Instrument That Can Hold Thousands Of Connections

Type: SUBPHASE TECHNICAL DOCUMENT
Identifier: PH-22.1
Parent: [PH-22](PH-22-distribution-under-thousands-of-observers.md)
Status: APPROVED
Created: 2026-09-03

---

## 1. Objective

Build the thing that can answer PH-22 §1, and prove it can fail.

Nothing in this phase may rest on an argument, and there is nothing to take a
measurement with. So the first subphase produces no optimisation and no
transport decision: it produces an **observer load harness** and the evidence
that the harness is honest.

## 2. Why an instrument gets its own subphase

Because this project's most expensive defects have all been instruments that
silently stopped measuring, and the pattern is consistent enough to plan around:

- `vitest.config.ts` was in no TypeScript program, so two options that do not
  exist were ignored for a whole cycle and the statistical suite had never run
  serially despite a comment saying it did (CA6-01).
- The browser suite reported six tests as **passed** while launching no browser
  (a6-03).
- A load runner reported a hundred assets costing **0.00 GB**, from 23,032 bars
  it had certainly written, because it measured a WAL file before its checkpoint
  (PH-21.2 §4).
- Dropping one glob deleted the entire browser suite with every gate step still
  green (CA7-16).

A load harness fails the same way and worse. A harness that opens two thousand
sockets and receives nothing on eighteen hundred of them reports a _better_
number than one that works — less server CPU, lower latency, no backpressure —
and every conclusion drawn from it is inverted. **The failure mode of this
instrument is reassurance.**

## 3. What the harness measures, and what it refuses to assume

| Quantity                    | How, and why not the obvious way                                                                                                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connections **established** | Counted on first byte received, not on socket open. An accepted socket that never delivers is the exact failure this instrument must not launder.                                                           |
| Connections **refused**     | Counted and reported by reason. A run with refusals is not a run at a lower connection count; it is a different experiment, and it says so.                                                                 |
| Delivery latency            | `receivedAt − tick.instant`. Every tick carries the engine's own instant, so this is end-to-end including server queueing, with no server instrumentation and no clock agreement needed beyond one machine. |
| **Gaps**                    | Per connection, by sequence. This is INV-002 under load: two observers of one asset must hold the same ticks. A silent gap is the defect that a throughput number would hide.                               |
| Duplicates                  | Per connection, by sequence. A resume that double-delivers is as wrong as one that skips.                                                                                                                   |
| Server cost                 | Measured on the **engine process**, by pid, not on the harness. A harness that measures its own CPU is the classic form of this mistake.                                                                    |

## 4. Isolation: the harness must not measure itself

The engine runs as its own process; the harness runs as its own; and the report
names both pids and both CPU figures separately. On one machine that still
shares a scheduler, so every run records the harness's own CPU alongside the
engine's — a run where the harness is the busier process is reported as
**instrument-bound** and its latency figures are not usable.

This is CA6-01's rule applied to a new instrument, and it is not theoretical:
the gate for this very subphase was killed on 2026-09-03 by a load-measuring
workflow sharing 7.6 GB with the statistical suite.

## 5. The plants this instrument owes

An instrument is not finished until it has been watched failing. Each of these
is a server the harness is pointed at, and each must produce a **loud** run
rather than a clean one:

1. **A server that refuses connections** past a limit. Expect: refusals counted
   and named, and the run marked incomplete.
2. **A server that accepts and never delivers.** Expect: established count far
   below attempted, not a fast, quiet, low-latency run.
3. **A server that drops ticks.** Expect: gaps counted per connection.
4. **A server that stalls mid-run.** Expect: latency divergence, not a silently
   truncated sample.
5. **A harness whose own workers are the bottleneck.** Expect: the run marked
   instrument-bound rather than reporting the server as slow.

## 6. Acceptance criteria

1. The harness opens, verifies and holds N real SSE connections against a real
   engine, for N spanning at least three orders of magnitude, and reports
   established / refused / gapped / duplicated per run.
2. Every one of §5's five plants produces a run that says so. Watched failing,
   recorded here.
3. The engine's cost is attributed to the engine's pid and the harness's to its
   own, and a run where the harness dominates is refused rather than reported.
4. A gate-affordable version runs in the statistical suite at a scale that
   finishes in seconds, guarding the harness's own contract rather than
   producing evidence.
5. The evidence run is recorded under `docs/evidence/`, on a quiet machine,
   naming the machine and the seed.

## 7. What this subphase does not do

**It changes nothing about delivery.** No shared serialisation, no
multiplexing, no transport decision. Those are PH-22.2 and PH-22.3, and they
are deliberately downstream of a number this subphase does not yet have.

**It does not tune anything.** If the first run shows the server falling over at
two hundred connections, that is the finding, and the fix belongs to the
subphase whose subject it is.

## 8. What the instrument found about itself

Two defects, both caught by planting, both of the class this subphase exists to
prevent.

**A plant that was unreachable rather than caught.** Marking an observer
established when the response callback fires — on headers rather than on a
byte — passed every test in the file. Node does not put headers on the wire
until the first `write`, so the silent-server test never reached the callback
and the plant could not run. `flushHeaders()` is what separates them, and it is
not exotic: it is what a server does when it has accepted a subscription and has
nothing to send yet. That test exists now, and the plant fails against it.

Before that, a plant applied through a string replacement that did not match was
a **silent no-op**, and the run it produced looked like a guard passing. The
anchor is asserted before every plant now. This is the repository's most-repeated
mistake, arriving in a new place.

**And the instrument's first two runs were wrong.** Ticks per observer read 6.0,
16.6 and 23.0 at one, ten and fifty observers — a rise that cannot be real,
because an observer's tick count is a property of its asset and not of how many
others exist. The engine was still warming: `open` resolved only after the whole
hold, so the run began measuring at the first socket and every size saw a
differently warmed engine. That is PH-21.2's archetype-rotation mistake in a new
instrument, and read uncorrected it says _delivery improves under load_.

Establishment and hold are separate phases now, the engine is warmed and the
warm-up discarded, and the sweep runs forwards and backwards.
