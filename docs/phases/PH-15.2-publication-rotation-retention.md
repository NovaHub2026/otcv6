## 1. Objective

Close the three exclusions PH-12 carried: where roots are published, how a key
is rotated, and how long the journal is kept.

## 2. Rotation is the one with a real result

`verifySignedChain` takes **one** public key and checks every link against it.
So today a rotated key produces a chain that fails verification — and fails it
the same way a forgery does. A verifier cannot tell "the operator changed keys"
from "someone else signed this", which means either the operator never rotates,
or verifiers learn to accept an unexplained key change. Both are worse than no
rotation.

The fix is that **the outgoing key names its successor**. A rotation is a record
signed by the key being retired, saying which key replaces it. A verifier holding
only the genesis key can then walk forward: each rotation is authorised by the
key it retires, so the chain of keys is as attested as the chain of roots.

## 3. The epoch is derived, not declared

A rotation gives an ordered list of authorised keys — genesis is epoch 0, each
rotation adds the next. Every `SignedCommitment` already records which key signed
it, so its epoch is the position of that key in the list. Nothing new is signed
and the canonical encoding does not change, which matters: changing what a
signature covers would invalidate every root already published.

The epoch is not a claim in the payload, so it cannot be lied about. A link
naming a key it was not signed by fails the signature check; a link naming a key
that is not authorised fails the key check.

## 4. A retired key must not be able to sign new history

This is the property that makes rotation worth doing. Without it, compromising
any key the venue has ever held still lets an attacker forge, and rotation buys
nothing.

Epochs must be **non-decreasing along the chain**. An attacker holding a retired
key cannot insert a link after the rotation, because that link's epoch would go
backwards. What they can still do is what they could always do: produce a
complete conflicting chain, which requires a second signature over a conflicting
root for the same range — and that is the evidence PH-12.2 said it was.

## 5. Retention derives from the dispute window, not from storage

The journal must be kept at least as long as a settlement can be disputed. That
window has never been set; setting it is the decision, and the storage follows.

The distinction that matters is between the two artefacts:

- **Journals may be pruned.** They are what makes a settlement _re-derivable_.
- **Commitments are kept forever.** They are what makes a change _detectable_,
  they are tiny — one per window rather than one per tick — and discarding one
  breaks the chain at that point permanently, because each root binds its
  predecessor.

So pruning loses the ability to recompute an old outcome and never loses the
ability to prove the record was not altered. A retention policy that pruned the
chain would quietly convert a provable record into an assertion.

## 6. Where roots are published

A root served only by the venue's own API proves nothing the venue could not
also rewrite. It needs an anchor the operator does not control.

The repository is public and independently hosted, which makes it one at no
cost: an append-only anchor file, committed on a cadence, gets third-party
timestamping and a tamper-evident history for free.

This subphase builds the **artefact and its verifier** — a canonical anchor
format, and a check that an anchor agrees with the chain it claims to summarise.
Wiring a credential to push it is an operational act with no code here.

## 7. What is built

`packages/distribution/src/rotation.ts`

- `verifySignedChain` extended to accept a rotation log.

`packages/distribution/src/retention.ts`

  consider a commitment pruneable at all.

`packages/distribution/src/anchor.ts`

- `buildAnchor`, `verifyAnchor` — a canonical, append-only summary of the chain.

## 8. Verification

| Claim                                                           | How               |
| --------------------------------------------------------------- | ----------------- |
| A chain spanning a rotation verifies from the genesis key alone | rotation battery  |
| A rotation not signed by the outgoing key is refused            | rotation battery  |
| A rotation whose `from` is not the current key is refused       | rotation battery  |
| A retired key cannot sign a link after its rotation             | rotation battery  |
| An unrotated chain still verifies exactly as before             | rotation battery  |
| A chain signed by a key never authorised is refused             | rotation battery  |
| Journals older than the dispute window are pruneable            | retention battery |
| A commitment is never pruneable, at any age                     | retention battery |
| An anchor that disagrees with its chain is refused              | anchor battery    |
| An anchor is append-only: an earlier entry can never change     | anchor battery    |

## 9. Out of scope

Pushing the anchor anywhere, credentials, and the schedule that does it. PH-15.3
takes the scheduling question for the assurance run; the anchor's cadence is an
operational setting recorded with the policy.

### A field removed because a plant could not fail

The anchor originally carried a `rootsDigest` — a hash over every root —
documented as committing "to the whole prefix, not just its end". Disabling the
check that used it left the entire battery green.

It was not a missing test. `commit()` folds `previousRoot` into every root, so
the chain is already a hash-chain and `headRoot` commits to the whole history by
construction. There is no chain this system can produce where the digest
disagrees and the head does not.

So the field was removed rather than propped up with a test that could only
assert it equals itself. A field in a _published_ artefact that reads as a
guarantee and cannot fail is worse than no field: it invites a verifier to rely
on something that is doing nothing. This is the "recorded number that nothing
reads" the project found once already, caught this time before it shipped.

### A check that survived because it was genuinely load-bearing

The `commitments` comparison in `extendsAnchor` also survived its first plant,
for a different reason: every test that would have exercised it was caught
earlier by the sequence checks. The case it alone covers is **re-windowing** —
the same tick range recommitted as fewer, larger windows, which leaves
`toSequence` untouched while destroying every root a counterparty was shown. A
test for that now exists, and the plant fails.

Two plants, two identical symptoms, opposite conclusions. Telling them apart
needed the question "what could this check refuse that nothing else does?"

### The decision recorded here

The dispute window is **90 days**, and the criterion is that a counterparty must
be able to raise a settlement dispute and have it answered from the record
rather than from the operator's word. Journals are kept at least that long;
commitments are kept forever, because each root binds its predecessor and
discarding one breaks the chain permanently. Roughly 33 million ticks at five
assets — hundreds of megabytes. If storage were the reason for the number, the
number would be wrong.
