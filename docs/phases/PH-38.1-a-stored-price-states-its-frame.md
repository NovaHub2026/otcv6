## 1. Objective

Give the tick record somewhere to say what its integers count in, and make the
production writer say it on every pass. Nothing is read differently yet and
nothing already stored is touched — this subphase only makes the fact
recordable, and makes it impossible to record a tick without it.

## 2. What is built

**A `PriceFrame`**, in a new `packages/runtime/src/priceFrame.ts`:

```ts
export interface PriceFrame {
  readonly logQuantum: number;
  readonly referencePrice: number;
  readonly displayPrecision: number;
}
```

Three fields, not one, and the phase document's §3 says why: display is
`referencePrice * exp(logQuantum * price)`, so the pair is what makes an
integer a price; `displayPrecision` is what makes it a string. Storing only the
quantum would be the same defect one release later, because `referencePrice` is
inside the personality fingerprint too
(`packages/runtime/src/personality.ts:26-29`).

**A `lattice` table in `record.db`**, beside `tick` and `seam`:

```sql
CREATE TABLE IF NOT EXISTS lattice (
  asset_id          TEXT    NOT NULL,
  from_sequence     INTEGER NOT NULL,
  from_instant      INTEGER NOT NULL,
  log_quantum       REAL    NOT NULL,
  reference_price   REAL    NOT NULL,
  display_precision INTEGER NOT NULL,
  PRIMARY KEY (asset_id, from_sequence)
) WITHOUT ROWID
```

Half-open by sequence: epoch _i_ covers `[from_sequence_i, from_sequence_{i+1})`
and the last one is in force. `RECORD_SCHEMA_VERSION` moves **2 → 3**, for the
reason version 2 moved: a reader that cannot see this table renders a price on
the wrong frame, so a downgrade must fail closed at open through the existing
`assertSchemaNotNewer` rather than quietly serve a wrong answer.

**The v2 → v3 migration writes nothing, deliberately.** A migration runs at
open, on any deployment, with no catalogue, no operator and no way to check
itself, so the only honest thing it can do is leave the range undeclared:
a sequence jump says a seam happened, not what the lattice was on either side,
and seeding from `LATTICE_BEFORE_PH37` would be wrong in a new direction on a
record that already holds post-change ticks.

Declaring the past is PH-38.2's subject, and it is separate precisely because
it is where this phase can do real damage. This document first said that
_nothing_ could soundly date those rows; PH-38.2 measured that claim false —
the record corroborates the old frame against itself at the relattice boundary
— and the correction is recorded there and in `DECISION-LOG.md`.

**`AssetBatch.frame` is required, not optional.** The compiler is a better
guard than a runtime refusal: a caller that omits a frame writes no epoch
silently, which is today's defect wearing a new hat. The cost was assumed to be
a wide mechanical diff and measured instead — **one** production construction
site (`apps/api/src/venue.service.ts:1174`) and three test files — so the
argument for optional does not survive its own price.

**The epoch is written inside the append transaction that already exists.**
After the first fresh tick of a batch is inserted, if the asset's newest epoch
is absent or differs from the batch's frame, an epoch row is inserted at that
tick's `(sequence, instant)`. One `BEGIN IMMEDIATE`, so two properties hold by
construction rather than by convention: **an epoch row can never exist without
a tick at it, and a tick can never be written under a frame the log does not
state.**

`MemoryTickRecord` mirrors it, the way it already mirrors `seamBetween`, and
the interface gains `frames(assetId)` and `frameAt(assetId, sequence)`.

## 3. The guard, and why it is the one the audit asked for

Cycle Audit 12's headline is that a release passed its full gate, passed hosted
CI on both jobs, and was broken in production anyway, in the one path no test
walks:

> The defect was not a missing test but a missing **test input**. Every test in
> the repository constructs its artefacts with the code under test. An upgrade
> feeds the _previous release's_ artefact to the _current_ reader, and nothing
> in the gate can produce one.

So the guard for this subphase does not synthesise a v2 file. It materialises
`v2.4.0` from git, builds it, writes a real `record.db` with **that** build, and
opens the file with **this** one — the recipe already proven at
`packages/engine/src/lattices.test.ts`, including the part that makes it honest:
symlink every `node_modules` entry **except** `@otc`, or the old tree imports
today's core and the test goes falsely green.

It asserts: the v2 file opens, is stamped 3, keeps every tick byte for byte,
and reports its pre-upgrade range as carrying **no** frame rather than the
current one.

Two further guards, each watched failing before it counts:

- A round trip: 2,000 ticks under `LATTICE_BEFORE_PH37['eurusd-otc']`
  (3.131447750503912e-7), close, reopen, 2,000 more under the current frame —
  two epochs, at the right sequences, and `frameAt` answering each range.
- A downgrade: a version-3 file opened by a reader that knows only 2 must
  refuse at open, not read on.

## 4. What is deliberately not done here

No read route changes, so no rendered price moves in this subphase. No candle
store changes. No contract change. The 3,728,119 already-undated ticks stay
undated and keep rendering exactly as wrongly as they do today — PH-38.1 stops
the bleeding for everything written from now on, and PH-38.2 and PH-38.3 are
what reach backwards.
