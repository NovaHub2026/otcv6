## 1. Objective

Replace the five hand-authored assets with the thirty, every number in the
catalogue produced by a recorded run, every per-asset constant re-measured, and
the statistical suite executed whole at thirty so its wall clock is a
measurement rather than PH-26.1's estimate.

## 2. What is built

1. **The run.** `npm run catalogue:build -- --label catalogue-of-thirty` draws,
   authors, calibrates and differentiates every seat in order, three replicates
   each, and writes the thirty compiled entries and an evidence table. The
   keyring label is in the file header with the command that regenerates it.
2. **The catalogue.** `ASSET_CATALOGUE` becomes the thirty. The five incumbents
   go, and with them the tests that were about them and nothing else: PH-4's
   amplitude-at-grain tables, PH-24.17's grain factors, the recalibration
   snapshot. Each is retired by name in this document rather than deleted
   silently.
3. **The re-measurements.** `MEASURED_LATTICE_TIE_RATES` for thirty assets,
   produced by `npm run evidence:ties` on the `ties-verify` family (twelve
   replicates of 8,000 horizons per asset, the verifying test's own procedure)
   and verified by `latticeTies.stat.test.ts` on `ties-fresh`; the
   horizon-coverage evidence regenerated for all thirty at all eight
   expirations — 240 rows, each a measurement — by `npm run evidence:horizons`
   run **one asset per process, six processes at a time**, because the fast
   tapes need ten simulated years each and thirty of them in sequence is
   seventeen hours of single-core time. The sections are composed into
   `docs/evidence/PH-11-HORIZON-COVERAGE.md`'s successor by a script that
   computes the totals from the headers rather than by hand.
4. **The twenty-six files.** Every test that named an incumbent by literal —
   `assetById('eurusd')`, `/markets/eurusd/…` — names the catalogue instead:
   `ASSET_CATALOGUE[0]!.definition.id`, or a seat by id where the test is about
   a particular character.
5. **A personality fingerprint on checkpoints.** Found while choosing the ids:
   a checkpoint carries no record of the personality that wrote it, so a state
   file written under one id would be resumed by a different personality under
   the same id. The thirty dodge it by never reusing an id; the runtime stops
   depending on that discipline by refusing to resume a checkpoint whose
   fingerprint is not the catalogue's.
6. **The whole suite at thirty**, with its wall clock recorded.

## 2.1 What the run taught, and what was retired by name

**Three builds, not one.** The first refused `dogeusdt-otc` at the dispersion
span guard — "needs 32.0 hours, this calibration spans 32.0" — because
`span / replicates × replicates` is not `span` in floating point and the guard
is strict; the builder now calibrates at one per cent over the span. The second
built all thirty, and `catalogue.test.ts`'s reproduction guard then failed all
thirty: the builder had derived its authoring streams under a run-wide keyring
while `registerAsset` derives under `registration-<id>`, so nothing could
re-derive an entry from its record. The builder now derives exactly as the
pipeline does, and the guard re-derives every one of the thirty. The third found
DOGE calibrated at **1.371%** ties against a 1% target: its dispersion fit needs
sixteen turnovers of a ninety-minute memory — a day and a bit — which is enough
for σ and far too few thirty-second horizons for a 1% quantile. The span is now
floored at the catalogue's ten-day calibration span. A settlement refund rate
is not a number to take from a short run.

**The thirty tie rates, measured.** `npm run evidence:ties` — twelve replicates
of 8,000 thirty-second horizons per asset on `ties-verify-<asset>-<n>`, the
verifying test's own procedure — ran all thirty in 6.5 minutes. Every one sits
below the 1% nominal target the quantum was calibrated to (highest
`btcusdt-otc` at 0.685%, lowest `eurusd-otc` at 0.400%), which is the same
"about half" the five showed: a tie is an integer-price event and the
calibration measures a continuous proxy for it. `latticeTies.stat.test.ts` then
verified a stratified sample on `ties-fresh`, a family the recording never
touched, each inside its own three-standard-error band. _Corrected by Cycle
Audit 9 (a3-03): the five first named here — `gbpjpy-otc`, `tsla-otc`,
`cgx-idx-otc`, `scx-idx-otc`, `evx-idx-otc` — were the family-stratified draw
of a version of the test before its stratum became the seat archetype; the
committed test at the phase gate drew `audusd-otc`, `gbpjpy-otc`,
`ethusdt-otc`, `scx-idx-otc`, `gmx-idx-otc`, and since Cycle Audit 9 (a2-01)
draws six, one per archetype._

**The DOGE display margin, recorded (Cycle Audit 9, a3-04).** PH-26 §7
promised this number and nothing carried it. `dogeusdt-otc`: quantum
3.5283e-6, display precision 7, so one display unit is 1/2.75 of a lattice
step at the reference price 0.078 — a **2.75× margin**. The displayed step
scales with the live price and the lattice step does not, so one step becomes
invisible on screen once the price falls below 1e-7 / 3.5283e-6 = **0.02834**,
a 63.7% fall from the reference. `displayPrecisionFor`'s guard checks only at
the reference price; the margin is a fact of the seat, and this is where it
lives.

**The 240 horizon cells, measured.** `npm run evidence:horizons -- --assets <id>`
one asset per process, fourteen at a time on sixteen cores: 18.7 CPU-hours in
about two and a half hours of wall clock, the longest single run `cgx-idx-otc`
at 8,402 s, plus `dogeusdt-otc` — the fastest tape — a second time under
another label as Run 3. Composed by a script that computes every total from the
headers: **40.43 billion ticks, 309.6 asset-years; 235 of 240 cells policed
below 0.2513pp**; worst |z| 3.12 (`usdjpy-otc` 4m), Benjamini–Hochberg at
q = 0.05 rejects nothing. The five cells that are not policed — the
fifteen-minute cells of `brx-idx-otc`, `eurjpy-otc`, `gbpjpy-otc`,
`solusdt-otc` and `usdchf-otc` — are named in the record with their floors:
their measured design effect at that horizon (1.14–1.35 against about 1.0–1.1
elsewhere) lifts the floor at most 0.024pp above the threshold at 350,000
windows. A longer run would police them; the record says so rather than
pretending. `horizonCoverage.stat.test.ts` re-derives all 240 rows, the totals,
the worst cell and the family-wise error rate from the record — after two of
its own regexes were taught that an id may carry a hyphen, which had parsed zero
rows from a 240-row record.

**Retired with the five, by name.** `packages/engine/src/recalibration.test.ts`
(PH-24.17's snapshot-restoration record, one describe over the five) is
deleted; `catalogue.test.ts`'s describe "re-authoring changed rhythm and grain,
never scale or tail weight" (PH-4's amplitude-at-grain tables, six of them) is
replaced by a retirement note that says why an emptied table would have been
worse than a deleted one. `registered()` in `catalogue.ts` went with the entries
it recorded.

**Twenty-six test files named an incumbent.** Every one now derives what it
needs — the first asset, the fastest tape, the slowest, a crypto pair, a second
currency pair — from `ASSET_CATALOGUE`, or, in the two browser suites that
cannot import the engine, from the service's own `/catalogue`. Two assertions
changed meaning on the way and are recorded: the push scheduler lands each burst
interval within ±1 ms and the test now tolerates what the scheduler declares,
having read 71 against 70 at a tempo the five never produced; and the hosted
venue's pace comparison — one asset against one over ten minutes — read the
fastest tape at 2,474 ticks against the slowest at 3,235 on one realisation, so
it is now five assets against five over an hour.

**The mirror window is measured against the fastest of the thirty.**
`btcusdt-otc` at 97 ms: 120,000 ticks is 3.2 hours, 10,000 is 16 minutes, and
the guard derives the fastest asset rather than naming it.

## 3. What this subphase may not do

- **It may not type a number into the catalogue.** Every entry is the builder's
  output; the file says so in its first line.
- **It may not keep an incumbent's constant for a new asset.** A record keyed
  by `eurusd` says nothing about `eurusd-otc`.
- **It may not sample where the phase boundary measures.** The evidence runs
  cover all thirty; only the per-gate suites sample.

## 4. Acceptance criteria

1. `ASSET_CATALOGUE` has exactly the thirty seats' ids, in seat order, and no
   retired id; `npm run catalogue:build` reproduces the file byte for byte from
   the recorded label.
2. Thirty lattice tie rates recorded and reproduced on a fresh stream family in
   the sampled suite; the full-catalogue verification recorded in evidence.
3. 240 horizon-coverage rows, every cell policed below the payout threshold or
   the shortfall named.
4. A checkpoint from a different personality is refused on resume, and the
   guard is watched failing.
5. The statistical suite runs whole at thirty, inside the hosted ceiling, and
   the wall clock is recorded.
6. Every guard watched failing against a planted defect.

### 5.1 Reproduction

`npm run catalogue:build -- --replicates 3` run again from the recorded seeds
after everything above, and compared with the compiled catalogue number by
number rather than as text (Prettier reformats the compiled file): **thirty
entries, thirty numeric literals each, every one identical, every string
identical.** The comparison script flagged one difference and it was its own —
the window it cut around the last entry ran into the `', '` of the error
message that follows it in the source. Criterion 1 holds: the catalogue is a
pure function of the seats and the seeds.
