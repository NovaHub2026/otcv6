## 1. Objective

A broker's operator has a state directory now holding checkpoints, a candle
history, a tick record, an asset registry and — when publication is on — a
commitment chain. This subphase makes that directory something an operator can
check, copy and put back, and closes the one open Issue about its files.

## 2. What is built

1. **Integrity at boot.** A `state:check`-shaped verification of the state
   directory before any market resumes: every checkpoint parses and is usable
   (`assertUsableRecord`), the record's head per asset is not behind the
   checkpoint's `lastPublished`, the candle history's stored head is not ahead
   of the record, and the three SQLite files open at a schema this code
   understands. A disagreement refuses the boot by name — the same policy as
   `CorruptRecordError` — rather than seaming past it.
2. **Backup and restore.** A documented, tested procedure: `sqlite3 .backup`
   is not required; `npm run state:backup -- --dir --out` writes a consistent
   snapshot of the directory — checkpoints copied whole, each SQLite file
   through `VACUUM INTO` — to a target path with a manifest, and a restore is
   a directory swap with the service stopped, verified by the boot check.
   (Planned as `POST /admin/backup`; a command, because a backup must not need
   the process — the decision log says why.) Asserted: a venue restored from a
   backup taken mid-run resumes, its record's head equals the backup's, and a
   client's resume from before the backup is honoured.
3. **The commitments file (Issue #19).** `readCommitments` takes the whole
   file as one string; after about six years the chain becomes unverifiable.
   Read it as a stream and verify it one link at a time, with the batch
   verifier's verdicts. (The file is not rotated: on disk it is bounded by
   disk, and a rotation would put the chain's order into file names.)
4. **The chain outlives the process** — found while building 3: every boot
   began a new chain at an empty root. The writer resumes at the file's tip and
   the ticks the previous process published past it are read back from the
   record; where the record cannot reach the tip the chain is restarted, never
   bridged.

## 3. Acceptance criteria

1. A corrupted checkpoint, a record behind its checkpoint, a history ahead of
   the record, and a newer schema each refuse the boot with the file and the
   asset named; a healthy directory boots.
2. A backup taken while the venue ticks restores to a venue that resumes
   without a seam and honours a pre-backup resume sequence.

   > **Corrected 2026-09-06 (Cycle Audit 10, a7-01 and a3-05).** This criterion
   > was met by tests that could not see the two ways it failed in an
   > operator's hands. (a) **Every backup the tool wrote refused to boot.**
   > `backup.json` — the manifest `backupStateDirectory` writes _into the copy_
   > — was read back as the checkpoint of an asset called `backup`, so
   > `state:verify` and the boot check both refused the copy with `backup.json
(backup): record belongs to asset undefined` until the operator deleted
   > the one file recording what the backup held. Nothing saw it because
   > `stateDirectory.test.ts` verified the copy and asserted only its heads,
   > `venueRecord.test.ts` restored by constructing a venue on the directory
   > and so never reached `main.ts`'s check, and the tool verified the copy
   > _before_ writing the manifest into it. (b) **A backup taken while the
   > venue ticks — the case this criterion names — could fail its own
   > verification**, because `record.db` was snapshotted before `history.db`:
   > a bar folded in between lands in a copy whose record does not hold the
   > ticks it came from, which is exactly what §3.1 refuses. The copy is
   > ordered checkpoints, history, record now; the manifest is skipped by its
   > `kind` rather than read as an asset; the tool verifies the copy after
   > writing the manifest; and the suite now backs up a directory a second
   > process is advancing, and boots the copy through
   > `stateRefusal(verifyStateDirectory(...))` the way `main.ts` does.

3. A commitments file is verified while holding far less than the file;
   Issue #19 is closed when this phase merges, with the number.
4. The chain continues across a kill, one chain per market; a chain the
   record cannot reach is restarted at an empty root and the break is visible.
5. Every guard watched failing.

## 5. What the subphase found

1. **Every boot began a new commitment chain.** `PublicationService` built a
   fresh writer at an empty root on every start; a broker verifying across a
   restart found one chain per boot. Not an Issue — nobody had verified across
   a restart — and the record built in PH-28.1 is exactly what continuing the
   chain needs.
2. **A lost record makes the restart republish**, and the chain shows it as a
   second genesis link starting at the resume point, overlapping the first.
   The test first assumed the restarted chain would begin after a gap; the
   truth is the overlap, and the assertion says so.
3. **The incremental verifier's pairwise check numbers links 0 and 1**; the
   verdict is re-numbered to the link's place in the file so that the batch
   and the streaming verifiers give the same words, which the test compares.
4. **`tsc` judges staleness by mtime too** (`--dry` after a content-restoring
   edit says "would build"), so the stale-build guard from PH-28.1 asks the
   right question and still needs a build after any edit under `tools/sim`.
5. **Two guards named the new pieces.** `publicSurface.test.ts` wants a
   binary entry point declared internal, and `labState.test.ts` wants the Lab
   refusal's exact expression in `main.ts`; both were satisfied as written
   rather than loosened.
6. **Hosted CI on the Cycle Audit 9 merge was red on a guard that was wrong
   about a clean tree** — the second such guard this phase. The documentation
   guard holds historical documents to git's history; hosted CI checks out
   one commit, so the history was empty and four documents naming a retired
   test failed. The guard now reads a shallow clone as no history, and CI
   fetches the history. The restart suite's early-exit error named an exit
   code and nothing else; it quotes the child now, and the stat leg re-run
   after these edits is the one this approval rests on: `servedRecord.stat` and `restart.stat`, serial, 5 passed, exit 0.
