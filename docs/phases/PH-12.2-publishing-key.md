# PH-12.2 — The Publishing Key, and Its Separation From Generation

Type: SUBPHASE TECHNICAL DOCUMENT
Identifier: PH-12.2
Parent: [PH-12](PH-12-verifiable-publication.md)
Status: APPROVED
Created: 2026-09-01

---

## 1. Objective

Make a commitment attributable: signed by a key that identifies the operator, and
that is structurally incapable of deriving the market.

## 2. The invariant at risk

`OTC_MASTER_SECRET` derives every stream in the market through HKDF (ADR-0002).
The convenient thing is to sign with it too — one secret to deploy, one to
rotate.

That would break **INV-010**. A signing key must live in every process that
publishes, be handled by operators, and appear in deployment configuration. If it
is also the generation secret, then anyone who obtains it obtains the keystream —
and a keystream snapshot is not a historical leak but a _forward_ one, worth hours
of future prices.

So the publishing key is generated independently and shares no derivation tree
with the master secret. **A process that can sign must not be able to generate.**

## 3. Discipline is not the mechanism

Stating the separation is worth nothing on its own. Three checks enforce it:

1. **Distinct inputs.** `OTC_PUBLISHING_KEY` is its own environment variable. The
   service refuses to start if it is missing, malformed, or **equal to
   `OTC_MASTER_SECRET`** — the last being the exact mistake an operator makes
   when wiring a second secret in a hurry.
2. **A source guard.** The signing module must not reference the keyring, HKDF,
   or anything in core's entropy surface. Checked by a guardrail test, and
   watched failing against a plant.
3. **Different algorithms, different shapes.** Ed25519 seed for publishing,
   ChaCha20 key material for generation. They are not interchangeable even by
   accident.

## 4. What a signature adds

PH-12.1 made a commitment identify a record. A signature makes it identify **who
committed to it**, which is what turns a root into something a counterparty can
rely on: an operator cannot later disown a published root, and cannot present a
different history without producing a second signature over a conflicting root
for the same range — which is itself the evidence of misconduct.

## 5. Scope

- Ed25519 signing and verification over a commitment.
- A signed root chain, and verification of it end to end.
- Key loading with the refusals of §3.1.
- The guardrail of §3.2, watched failing.

## 6. Exclusions

- Key custody, rotation procedure and distribution of the public key. The
  mechanism must permit rotation — the signed chain records which key signed each
  root — but running it is operations, and no private key enters the repository.

## 7. Acceptance criteria

1. A signed commitment verifies under the right public key and fails under any
   other.
2. Any alteration to the commitment invalidates the signature.
3. Loading refuses a missing key, a malformed key, and a key equal to the
   generation secret.
4. The guardrail fails when the signing module is made to import the keyring.
5. A signed chain verifies end to end, and reports the link where it breaks.

## 8. Subphase approval record

**APPROVED** from executed evidence, 2026-09-01.

### Against the acceptance criteria

1. **Signature verifies under the right key, fails under any other** — including
   the case that matters most: a forger who supplies both a signature and a
   public key. `verifyCommitment` requires the caller to name the identity they
   trust, and a swapped-in key fails even when internally consistent.
2. **Any alteration invalidates** — asset, from, to, count, previous root and
   root are each mutated in turn, because a signature over the root alone would
   leave unattested exactly the fields that say what the root _means_.
3. **Loading refuses** a missing key, a malformed key, and a key equal to the
   generation secret — the last case-insensitively, since that mistake arrives as
   a copy-paste.
4. **The guardrail fails on a plant** — watched, twice.
5. **A signed chain verifies end to end** and reports structure before
   attribution, because reporting "bad signature" for a missing window sends an
   investigator the wrong way.

### What the subphase learned

**The guard's first version banned the wrong thing.** It listed
`OTC_MASTER_SECRET` among the identifiers the signing path must not contain, and
fired immediately — on the line that _is_ the defence, the refusal of a publishing
key equal to the generation secret.

Banning the name would have forced that check somewhere it could be skipped,
trading a guaranteed refusal for a tidier scan. The list now covers what actually
grants the capability — `MasterKeyring`, `deriveKey`, `hkdf`, `chacha`,
`RandomSource`, without which keystream is unreachable — and the exemption is
paired with a **positive** check: the guard asserts the refusal is still present.

That is the difference between a guard that says "the attack is absent" and one
that says "the defence is there". Only the second notices when someone deletes
the defence.

Both halves were watched failing: a planted `MasterKeyring` import, and a reworded
refusal.

### Known limitations carried forward

- Key rotation is supported by the format — each signed commitment records the
  public key that signed it — but no rotation procedure exists. Operations.
- Nothing emits signed commitments yet. PH-12.3.
