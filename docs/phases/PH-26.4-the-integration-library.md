## 1. Objective

_"Quiero integrar todo el motor de OTC y el panel admin junto con el Lab a mi
broker… solo crea un archivo de integración como guía."_ — and then: _"una
biblioteca de 30 activos ya predefinidos listo para integrar."_

The thirty are compiled, calibrated and served. What a broker integrating this
engine needs is not the catalogue's source but **the catalogue as a fact they
can consume**: which assets exist, under which ids, at which precision, with
which reference price and which character — and a guarantee that what they read
is what the engine hosts.

## 2. What is built

1. **`GET /catalogue` is the library.** It already reports every hosted asset
   with its id, display name, family, reference price, display precision,
   quantum, mean interval and tie rate. PH-26.4 makes it complete for an
   integrator: the seat's `character`, `archetype` and `priceSource` join the
   response, so a broker's screen can say what an instrument is without a
   second lookup, and nothing about an asset lives only in the source.
2. **`docs/integration/CATALOGUE.md`** — the thirty in one table for a human:
   id, name, family, archetype, reference price with its dated source,
   precision, and the one-paragraph character — generated from the compiled
   catalogue by a script, never typed, with the command that regenerates it.
3. **the integration package’s `INTEGRATION.md` §3.1** — how to read the library
   over HTTP, what is stable (ids, precision, quantum) and what an operator may
   change (display name, live/retired), and the one rule an integrator must not
   break: an asset id is a key-derivation label and a state filename, and the
   thirty ids are the only ids the engine will ever have hosted under this
   catalogue.
4. **A guard that the library and the catalogue agree**: the generated table
   is re-derived from `ASSET_CATALOGUE` and `ASSET_SEATS` in a unit test, so an
   edit to either without regenerating the other fails by name.

## 3. What this subphase may not do

- **It may not expose anything that reconstructs a future price.** The
  response carries what `GET /catalogue` already carried plus prose; no trait
  vector, no keyring label, no cursor (INV-010).
- **It may not let the integration copy drift from the engine.** The table is
  generated, and the guard says so.

## 4. Acceptance criteria

1. `GET /catalogue` carries `archetype`, `character` and `priceSource` for every
   compiled asset, and `null` for a runtime-registered one that has no seat.
2. `docs/integration/CATALOGUE.md` lists exactly the thirty, regenerated by a
   recorded command, and the unit guard fails when it is stale.
3. `INTEGRATION.md` documents the library and the id rule.
4. Every guard watched failing against a planted defect.

Only executed checks are reported (§68). Targeted gate on
`feature/ph-26-catalogue-of-thirty`:

```

```

`GET /catalogue` carries `seat: { archetype, character, priceSource }` for every
compiled asset and `null` for one without a seat; `docs/integration/CATALOGUE.md`
is written by `npm run catalogue:library` and compared byte for byte by
`catalogueLibrary.test.ts`, which is why the file is Prettier-ignored — a
formatter that pads table cells would make the generator and the file disagree
about whitespace and nothing else.

Guards watched failing, each against a planted defect and restored:

| Plant                                          | Caught by                                |
| ---------------------------------------------- | ---------------------------------------- |
| one price edited in the table on disk          | `docs/integration/CATALOGUE.md is stale` |
| a seat's character edited without regenerating | the same, from the other side            |
| `seatOf` answering null for every asset        | `eurusd-otc has no seat`                 |

One guard was wrong before it was right: both INV-010 checks first forbade the
_word_ "volatility" and failed on a seat whose character mentions a volatility
state. They forbid trait-shaped fields, keyring labels and cursors now.
